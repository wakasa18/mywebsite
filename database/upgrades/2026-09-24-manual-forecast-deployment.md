# Manual forecast filters and saved records

Package: `build/hostinger-manual-forecast-2026-09-24.zip`.

No SQL import or database migration is required. This patch assumes the current reports UI and shared staff layout are installed.

## Upload

Back up and replace:

- `public/assets/js/reports.js`
- `app/Views/admin/reports/index.php`

Upload the JavaScript first, then the view. If your public directory is mapped to `public_html`, upload the JavaScript to `public_html/assets/js/reports.js`. Keep the view in the existing application's `app/Views/admin/reports/` directory. Reload the Reports page after uploading; the script URL includes a new cache version.

## Behavior

Changing the forecast interval or dates now leaves the displayed forecast unchanged until **Update Forecast** is submitted. A reminder appears when forecast selections differ from the displayed results. Other report filters retain their existing automatic submission behavior.

**Update Forecast updates the preview only.** Saved Forecast Records contains daily product snapshots across all branches, generated by the existing forecast command. It shows the latest 100 records, newest first. The page now explains this distinction.

## Saved records on Hostinger

The saving and history-query logic passed isolated database tests. The Hostinger database and cron configuration have not been checked remotely.

Configure one daily cron task using the actual PHP CLI and application paths, as described in `HOSTINGER-DEPLOYMENT.md`. The command is:

```sh
php spark forecast:reorder
```

Run it from the application's directory containing `spark`, or give `spark` its absolute path. It writes daily snapshots for eligible low-stock products across branches. If there are no eligible products, no records are added. Sequential reruns on the same day skip products already saved; avoid overlapping runs. The next day can add new snapshots. Forecast preview selections do not change the job's default sales-history window.

To inspect existing records without changing data, select the application database in phpMyAdmin and run:

```sql
SELECT COUNT(*) AS saved_records, MAX(generated_at) AS latest_snapshot
FROM forecasting_data;
```

After the scheduled job runs, reload Reports and check Saved Forecast Records. An empty history alone does not prove that saving is broken: check job execution and whether any products qualify.
